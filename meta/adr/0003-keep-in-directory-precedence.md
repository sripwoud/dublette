# Keep-in directory precedence over intrinsic ranking

The keep policy ranked group members purely by intrinsic quality (fidelity for recording-match audio, alphabetical otherwise), which cannot express "this tree is authoritative": deduplicating a staging inbox against a curated beets library (#42) kept the staging copy in 1 of 35 cross-tree groups, marking a `library.db`-referenced file for deletion and making `-y` unusable for that workflow. `--keep-in <DIR>` (repeatable, order = precedence) pins the survivor: when any group member lies under a keep-in directory (first-listed wins), keep candidates restrict to the members under it and the existing per-kind ranking breaks ties among them; every other member becomes a deletion; groups with no such member select exactly as before, and runs without the flag are unchanged. The restriction is applied once in `plan` after grouping — one shared site instead of threading it through the three per-kind selection paths — because it changes only selection within a group, never membership. Containment is a canonicalized-ancestor check (`Path::starts_with` after `canonicalize`, component-wise, so `/lib/foo` never matches `/lib/foobar`): keep-in directories are validated and canonicalized fail-fast in the CLI shell before scanning (exit 2, mirroring scan-directory validation), the config carries canonical paths, and members canonicalize at check time so relative paths, trailing slashes, and symlinked forms match. A keep-in directory need not be a scanned directory — a subdirectory of a scanned tree is legitimate.

Rejected: **`--prefer-dir` / `--authoritative` naming** (keep-in states the mechanism — containment — rather than a vaguer intent); **threading the restriction into each keep-selection site** (three copies of one rule); **implicit authority from scan-directory order** (silently changes selection for every existing multi-directory run; an explicit flag keeps default behavior byte-identical); **moving survivors into the keep-in directory** (dublette deletes, it does not organize); **filtering scanning to keep-in trees** (files outside them must still be scanned, grouped, and deletable); **per-media-kind variants and config-file equivalents** (no demonstrated need). Revisit triggers: demand for per-kind keep policies, survivor relocation, or a policy-file confirmer (which would also revisit ADR 0001's inline confirmer).
